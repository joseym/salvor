# npm/salvor-cli

This is the npm package published as `@salvor-run/cli`, the `npm install -g
@salvor-run/cli` door onto the `salvor` binary.

It is repo-owned rather than generated by `dist` (cargo-dist). `dist`'s own
npm installer template has no override point for this: the package it
generates always ships a Node.js relay (`spawnSync` into the downloaded
binary) as the `salvor` entry point. That relay cannot be killed. Sending
SIGTERM, SIGKILL, or Ctrl-C to the relay's PID kills the relay; the real
`salvor` process it spawned has no parent left to notice and keeps running
the durable run to completion, orphaned. For a product whose entire pitch is
"kill it, resume it," that is disqualifying for the npm door specifically
(the other three doors, shell, PowerShell, and Homebrew, all install the
binary itself, with no relay in front of it).

## The fix

`postinstall.js` downloads the platform's `salvor` binary as before, then
(on POSIX) overwrites `bin/salvor`'s own bytes with that binary's bytes and
marks it executable. npm's bin symlink for a global or local install points
at that same file path; it does not care what bytes live there. After the
swap, launching `salvor` execs the real binary directly. There is no
Node.js process in between to kill, orphan, or race, so `kill -9` on the
launched PID stops the run immediately.

`lib/binarylink.js` and `bin/salvor` are the fallback for the cases where
the swap cannot happen:

- Windows, always: npm's generated `.cmd`/`.ps1` shim invokes `node
  <target>` itself, never exec's the target file's own bytes, so the entry
  point has to stay a real Node script there.
- `--ignore-scripts` installs, where postinstall never runs.
- A postinstall that ran but failed to swap (permissions, a corrupted
  download, etc.) logs a warning and leaves the relay in place rather than
  failing the install.

The fallback relay downloads on first invocation if needed (so a clean
prefix with `--ignore-scripts` still works, just lazily), then attempts the
same swap itself before running, so it only has to relay once. When it does
relay, it forwards SIGINT, SIGTERM, and SIGHUP to the child and mirrors the
child's exit status, including the 128+signal convention for a signal
death. That is everything a wrapper process can do. It cannot forward
SIGKILL: the OS delivers SIGKILL to the wrapper without giving it a chance
to run any JavaScript at all. That asymmetry is exactly why the fix above is
"stop having a wrapper," not "make the wrapper better at relaying."

## What has to stay in sync by hand

`lib/platforms.js`'s `supportedPlatforms` map mirrors `dist-workspace.toml`'s
`targets` list and the archive names `dist` produces for each target. It
used to be generated; now it is hand-maintained. If a target triple is added
to or removed from `dist-workspace.toml`, update this file's map to match in
the same change.

## Release

`.github/workflows/npm-cli.yml` stamps this package's `version` to the
pushed tag and publishes it to the npm registry on every `v*` tag, the same
trigger the rest of the release pipeline uses. It is a separate, hand-owned
workflow file rather than a job inside `release.yml`, because `release.yml`
is regenerated wholesale by `dist generate` and would drop a hand-added job
the next time that runs (`npm-client.yml`, which publishes the TypeScript
SDK, exists as its own file for the identical reason). See
`docs/RELEASING.md`'s npm section for the user-facing description.
